# 流式故障切换网关（FastAPI + 两个可复现本地模拟节点）

在网页输入提示词与输出词元上限，观察回复**按批生成**；网关把同一节点按原
顺序采纳的词元合成 `token_batch` 事件，凑满 3 个立即发送，否则从本批首个
词元入批起最多等 250ms（上游停顿时也到时发出）。首节点（node-a）中途
超时后，网关用「原提示词 + 已采纳词元」让备用节点（node-b）续写，切换
节点或结束回复前先把当前批次发完。网关只追加新词元、忽略首节点迟到回包，
整条回复共用一个词元上限；接续成功时结果与无故障场景**逐词元完全一致**；
两节点模型/分词器版本不一致或备用续写失败时，保留已显示文本并标记为
**未完成**。

## 架构

```
浏览器 (web/)  ──SSE──▶  网关 gateway/app.py  ──SSE──▶  node-a (首节点)
                          │  读超时/出错后                │  挂起后仍产生
                          └──────────────▶  node-b (备用)  └─▶ 迟到回包（被忽略）
```

* `common/deterministic.py`：确定性「解码」。第 i 个词元是
  `sha256("mock-llm/v1:" + prompt + ":" + i)` 对共享词表取模的纯函数，无随机数、
  无时钟、无机器标识。两个节点共用同一模块，因此健康续写必然复现同一词元流，
  结果可复现（同提示词多次请求、跨节点结果一致，有测试覆盖）。
* `node/app.py`：同一个 FastAPI 应用部署为 node-a / node-b 两个实例，SSE 流式
  输出 `meta / token / error / done` 事件；支持按请求注入挂起、失败、版本伪装，
  并在挂起后由脱离请求的后台任务继续产生「迟到回包」（记录在 `/debug/late`）。
* `gateway/app.py`：编排状态机，负责读超时判定、只追加接受、共享预算、身份校验
  与故障切换，并把已采纳词元按批（`TokenBatcher`）合并成 `token_batch` SSE 事件
  转发给浏览器。
* `web/`：原生 HTML/CSS/JS 单页，**每个 `token_batch` 只做一次 DOM 追加**
  （按来源节点着色）、展示已采纳词元数/批次数/切换/未完成事件，并自动与
  `/api/expected` 的无故障基准核对。

## 启动

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://localhost:8080
```

三个服务：node-a、node-b（仅内网 expose，带健康检查）、gateway（映射 8080）。
节点每 0.12s 出一个词元，网关读超时 `GATEWAY_READ_TIMEOUT=1.0s`，挂起场景会在
约 1s 后触发切换。网关批量参数 `TOKEN_BATCH_SIZE=3`、
`TOKEN_BATCH_MAX_WAIT_MS=250`（可经环境变量覆盖）。

### 无 Docker 时本地运行（本机试跑所用方式）

```bash
python -m pip install -r requirements.txt
python run_demo.py          # 真实 uvicorn + HTTP 跑全部 4 个场景并打印核对报告
python -m pytest            # 15 项端到端/单元行为测试（含批量行为）
```

## 四个演示场景（网关侧按请求注入，可重复）

| 场景 | node-a 行为 | node-b 行为 | 最终结果 |
|---|---|---|---|
| `healthy` | 正常生成 | 不参与 | 12/12 词元，基准结果 |
| `failover_success` | 第 4 个词元后挂起 → 网关读超时 | 用原提示词 + 4 个已采纳词元续写 | 12/12，与 healthy **完全一致** |
| `failover_backup_error` | 同上挂起 | 续写至绝对下标 7 时失败 | 保留 7 个词元，标记未完成 |
| `version_mismatch` | 同上挂起 | 伪装为 `mock-llm-7b-hotfix` / `tok-v2` | 拒绝接续，保留 4 个词元，标记未完成 |

## 需求与实现的对应

1. **网页输入提示词与词元上限、按批生成**：`web/index.html` + SSE，每个
   `token_batch` 事件触发一次 DOM 追加，词元计数与批计数实时更新；页面仍保留
   对裸 `token` 事件的兼容处理。
2. **词元按批下发，减少 SSE 事件与网页更新次数**：网关 `TokenBatcher`
   （`gateway/app.py`）把同一节点按原顺序采纳的词元攒成 `token_batch`：
   * 凑满 `TOKEN_BATCH_SIZE`（默认 3）个立即发送；
   * 否则从**本批首个词元入批**起最多等 `TOKEN_BATCH_MAX_WAIT_MS`（默认
     250ms），等待基于独立定时器，**上游完全停顿时也会到时发出**；
   * 切换节点（`fallback` 前）与任何结束事件（`done`/`incomplete`）前，先
     `flush` 当前批次，因此批次不会跨节点、词元也不会滞留；
   * 批次内每个词元保留原有绝对 `index`、`id`、`text` 与来源 `node`，网页
     每批一次追加并显示词元数、批次数与完成状态。
3. **首节点中途超时与迟到回包**：节点收到 `stall_before` 后挂起；网关用
   `asyncio.wait_for` 做**逐事件读超时**（不是整体请求超时）。挂起节点脱离请求
   的后台任务 1.5s 后继续产出迟到词元并打日志/落 `/debug/late`。
4. **备用节点用原提示词 + 已采纳词元续写、共用原词元上限**：网关携带 `prompt`、
   `start=已采纳数`、`accepted_ids`、剩余预算（`max_tokens - 已采纳数`）调用
   node-b；节点侧对 `accepted_ids` 做前缀校验（不匹配返回 409），全流总量恒等于
   一个上限。
5. **只追加、忽略迟到输出**：网关维护 `next_index`，只接受严格等于下一下标的
   词元，重复/乱序（含迟到）一律忽略；前端有同款下标守卫。
6. **接续成功与无故障一致**：确定性解码 + 绝对下标续写，测试与页面对照
   `/api/expected` 双重断言词元 id 序列逐位相同。
7. **版本不一致 / 续写失败 → 保留已显示文本并标未完成**：切换前网关先 GET
   node-b `/info` 比对 `(model_id, tokenizer_version)`，不一致直接发 `incomplete`
   且不发起续写；续写流返回错误或提前结束同样发 `incomplete`，事件中带回完整
   `prefix_text`，已下发批次（词元）不会被撤回或改写。

## SSE 事件（网关 → 浏览器）

`meta`（请求信息，含 `batch_size`/`batch_max_wait_ms`）→ 若干 `token_batch`
（`{"tokens": [...]}`，每批 ≤3 个同节点词元，词元含绝对下标 index、词元 id、
text、来源 node）→ 可能的 `fallback`（切换原因与已采纳数，其前当前批次已
发完）→ 更多 `token_batch` → `done`（完成，含各节点词元占比）或 `incomplete`
（原因、身份信息、保留前缀）。网关不再下发裸 `token` 事件；前端仍保留对它的
兼容分支。

## 验证结果

本机（无 Docker，使用真实 uvicorn socket）已跑通：

* `python -m pytest`：**15/15 通过**。原 8 项（健康基准、接续等价性、共享预算、
  备用失败、版本不一致、迟到回包被忽略、节点前缀校验、跨节点/跨次确定性）在
  `token_batch` 协议下全部保持；新增 7 项覆盖 `TokenBatcher` 单元行为
  （凑满即发、250ms 超时、显式 flush、批次不混节点）与集成行为（healthy 为
  有序 `[3,3,3,3]` 批、切换前先发完首节点批次、备用失败仍发完全部已采纳批次）。
* `python run_demo.py`：四个场景全部通过自动核对，报告打印每个场景的批次大小。
  healthy 为 4 批 `[3,3,3,3]`；failover_success 为 5 批 `[3,1,3,3,2]`（首节点
  4 个词元在切换前全部发完），最终词元序列与 healthy 逐位相同；两个失败场景
  保留前缀与基准同位置前缀一致；node-a 被放弃后确实产生了迟到词元且均未被采纳。
* 250ms 停顿超时专项：让节点只发 1 个词元即完全挂起（凑不满 3 个），验证部分
  批次仍在首批入批后约 250ms 由定时器发出，不依赖上游再产词元。
* 浏览器等价冒烟：按 compose 同款参数起三个真实 uvicorn 进程，`/`、`/app.js`、
  `/styles.css` 均 200，四场景 SSE 全量解析，断言批大小上限、严格下标顺序、
  单节点批次、来源着色信息与失败前缀保留。

## 遗留事项与简化

1. **Docker Compose 文件未在本机构建验证**：当前环境没有 docker 守护进程；
   compose/Dockerfile 仅做了 YAML 与结构校验，且网关/节点代码未改动进程模型
   （仍是同一 uvicorn 入口，仅新增两个带默认值的环境变量）。首次
   `docker compose up --build` 建议在有 Docker 的环境确认一次（镜像基于
   `python:3.11-slim`，结构与本地 uvicorn 启动方式一致），然后打开
   http://localhost:8080 在推理页试跑正常生成、节点切换与备用失败。
2. 故障注入是**演示机制**：场景表和 `X-Mock-*` 头只用于可重复演示，生产网关
   不会信任节点的自我身份声明；真实系统应改用带外配置/证书校验模型身份。
3. 仅模拟单一首要→单一备用、一次切换；未实现多级备用、重试退避、熔断与
   跨请求持久化（迟到回包记录保存在节点内存中，重启即失）。
4. 确定性「模型」用词表哈希代替真实推理，重点是可复现的词元契约与切换语义，
   不代表真实 LLM 的解码质量。
5. 前端为零依赖原生页面，未做无障碍/国际化等增强；接口仅做了基本入参校验
   （提示词长度、词元上限 1–128）。
